# Repository context contract

Repository context is a bounded, immutable source snapshot for the existing single-operator pilot. It informs proposals; it is not proof of deployed behaviour or an independent business oracle. Human expectations still take precedence over implementation-derived values.

## Import and review

`POST /api/projects/{id}/repositories/sync` accepts `{provider?: "github"|"azure", repository: string, ref: "main", role: "frontend"|"backend", paths: string[]}`. `paths` contains 1–20 exact repository-relative text file paths; the operator explicitly chooses what may be imported. Omitted `provider` defaults to GitHub; GitHub uses `owner/name` and optional `X-QA-GitHub-Token`, sent only to the fixed GitHub API origin. Azure uses a full `https://dev.azure.com/organization/project/_git/repository` URL and optional `X-QA-Azure-PAT`, sent as HTTP Basic authentication only to `https://dev.azure.com`. Credentials for the wrong provider (including both headers) are rejected. No token is stored, logged, or forwarded to the model. GitHub public repositories work without a token. Azure may require a Code (Read) PAT even for a public repository because its Git object APIs can deny anonymous access; the form reports this clearly. Private repositories require a read-capable token for each sync. Azure PATs need **Code (Read)** access for the selected repository. Tokens are cleared from the form on submit, cancel, provider change, project change, or disconnect.

The importer resolves the ref to a commit SHA, reads all requested files at that commit, and returns errors rather than silently dropping or truncating files. Only regular text blobs are accepted, no symlinks/submodules. Reject environment/key/credential files, binary content, recognizable embedded secrets, unsafe paths, and oversized content. These checks are an aid, not a guarantee that source contains no sensitive material; review the complete imported content before consenting to send it to a provider. Limit to 40,000 bytes of file content per snapshot and 60,000 bytes of assembled proposal context. Import never executes repository code.

`GET /api/projects/{id}/repositories` returns at most 100 newest snapshot summaries as an array. Summary fields: `id`, `project_id`, `provider`, `repository`, `ref`, `role`, `commit_sha`, `content_sha256`, `file_count`, `total_bytes`, `created_at`.

`GET /api/projects/{id}/repositories/{snapshot_id}` returns the summary plus `files: [{path, content}]`. Creating a new snapshot does not mutate earlier records. Re-sync uses the same form and produces a new snapshot pinned to the newly resolved commit. The initial UI supports deliberate sync; automatic webhook sync comes after this contract.

## Agent file search

Choose **Let the agent find files** to import source for a targeted request. Supply the repository/ref/role and testing request, choose the existing AI connection/model, and consent to sharing the request plus repository file names and sizes. You do not need to know any file paths. OpenAI managed/BYOK, ChatGPT subscription, Anthropic, Google Gemini, and OpenCode Go use the same connection rules as proposals.

`POST /api/projects/{id}/repositories/search` accepts `{repository: {provider, repository, ref, role}, ai: {provider, model, credential_mode, chatgpt_profile_id?, prompt, consent}}`. Transient repository and model credential headers match the existing importer and planner. It returns `{snapshot: RepositorySnapshot|null, reason, candidates, excluded}`. No model context supplied by the caller is used. The model receives a sorted inventory pinned to one commit, never repository tokens or file contents. It must select only listed paths, with no duplicates, at most 20 files and 40,000 total bytes. An empty selection returns the explanation without saving a snapshot. Invalid model selections fail without importing or saving anything.

Inventory traversal reads nonrecursive Git trees using the same provider object APIs as manual import. It excludes credential paths, symlinks/submodules, common generated/dependency directories, unsupported binary formats, and individual files over 40,000 bytes. Eligible formats cover common source languages, tests, configuration and documentation. Search is bounded to 64 metadata requests, 2,000 eligible files, 55,000 estimated inventory bytes, and 20 directory levels; incomplete/oversized trees fail visibly instead of silently selecting from a partial inventory. Larger repositories currently require manual import. Exclusion counts refer to entries (an excluded directory counts once).

The selected contents are imported at the inventory's commit, checked with the existing text/secret policies, persisted as an immutable snapshot, and opened for full review. A moving branch cannot change the source between selection and import. The user then selects the reviewed snapshot in Chat/proposals and separately consents to sending its contents. Finding relevant files does not itself run tests, approve scenarios, or establish business expectations. Automatic selection is based on names and sizes; the model has not read the contents at that stage.

## Azure Repos details

Azure DevOps **Services** Git repositories are supported. Self-hosted Azure DevOps Server, TFVC, SSH clone URLs, and legacy `visualstudio.com` URLs are not supported; use the canonical `dev.azure.com` URL. Project and repository names containing spaces are URL-escaped. Arbitrary hosts, URL credentials, queries, fragments, and path traversal are rejected.

A bare ref means an Azure branch (for example `main` or `feature/login`). Use `refs/tags/v1` for tags, `refs/heads/main` for explicit branches, or a full 40-character commit SHA. Ref prefix matches are never accepted as exact matches. Annotated tags are peeled to commits. Ref lookup is bounded to 1,000 prefix matches; if the exact ref is absent, provide its full commit SHA. The commit's tree is resolved once; selected regular files are fetched by immutable blob IDs. Symlinks and submodules are rejected. Git LFS is not resolved.

Authentication currently uses an import-only PAT, matching this local pilot's transient GitHub token flow. Microsoft recommends [Microsoft Entra authentication for production integrations](https://learn.microsoft.com/en-us/azure/devops/organizations/accounts/use-personal-access-tokens-to-authenticate?view=azure-devops); account sign-in/OAuth and automatic sync remain future work. Protocols follow Microsoft's [refs](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/refs/list?view=azure-devops-rest-7.1), [commits](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/commits/get?view=azure-devops-rest-7.1), [trees](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/trees/get?view=azure-devops-rest-7.1), and [blobs](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/blobs/get-blob?view=azure-devops-rest-7.1) APIs (7.1).

## Proposals

A proposal can include `repository_snapshot_ids: string[]` with unique snapshots from the same project, in selection order. One plan can use multiple frontend and backend repositories from GitHub and Azure Repos. All sources, application context and browser observations share the 60,000-byte context limit. The server builds one bounded context from operator context and snapshot headers/files; validation and consent apply to that final text. The response adds `repository_snapshots`, containing the selected summaries. The existing `context_sha256` hashes the complete context actually sent. No server-side latest-ref lookup can silently replace a selected snapshot.

Frontend snapshot selection shows repository, role, commit, included paths and full content for review. Selecting a snapshot or editing context resets consent. Disconnection, project changes and cancelled requests discard transient token state. Generated scenarios remain unapproved.

## Implementation boundary

`internal/repository` owns the bounded GitHub and Azure DevOps Services client and concrete import types: `Input {Provider, Repository, Ref, Role, Paths}`, `File {Path, Content}`, `Snapshot {Provider, Repository, Ref, Role, CommitSHA, ContentSHA256, Files, TotalBytes}`; `New(http.RoundTripper) *Client`; `Client.Fetch(context.Context, Input, token string) (Snapshot, error)`. Export sentinel errors `ErrInvalid`, `ErrUpstream`, `ErrAccess`, `ErrTimeout`, `ErrBusy`. The client has a 45-second deadline, at most two concurrent imports, no redirects/retries, bounded response bodies, and no arbitrary network destinations.

`internal/qa` owns persistence summaries and project scoping; HTTP owns import orchestration. HTTP import request timeout is 50 seconds. Snapshot contents are stored in PostgreSQL for this local pilot. Repository search has a 185-second request deadline (bounded inventory, model selection, import); the server write timeout is 190 seconds. Other endpoint deadlines remain unchanged.

## Whole-app discovery

In **Settings → Repositories**, connect a ref and role without selecting files. A whole-app request uses these connections plus the latest import from each additional project repository. Connecting an existing repository updates its ref and role. For recurring private reads, **Save read access** encrypts the token for this project and provider repository. **Forget saved access** removes the stored token. **Disconnect** excludes a repository from future whole-app requests and keeps its earlier imports and plans available for review. The server's 32-byte local encryption key lives under the user configuration directory in `qa-agent/repository-access`; set `QA_REPOSITORY_STORAGE_DIR` to use a persistent private directory.

Whole-app consent covers file names and the eligible contents selected for each repository. The scan examines up to 2,000 eligible file names per repository and ranks the files that provide evidence for distinct features. It reads the selected files in batches of up to 20 files and 40,000 bytes each, saving progress between batches. The review shows how many eligible files were read. Files larger than 40,000 bytes are currently excluded from the inventory. Public GitHub files are fetched at the pinned revision and verified against their Git blob identifiers. The same source and secret filters as snapshot imports apply. A partial file inventory, unavailable repository, or fallback to a saved import appears in the review. The final model call combines validated journey summaries within a separate 180,000-byte budget, sharing that space across the source journeys. The plan can contain up to 50 reviewable checks. The plan also groups source-backed journeys that need setup. Each shows its intended outcome, the prerequisites needed to make it runnable, and its evidence. Only executable checks can be approved. Additional source findings remain available for review. Source summaries, paths and commit IDs are saved with the request so the reviewed evidence survives a reload.

In an existing plan conversation, type **save the [name] journey** to track one proposed flow separately in Coverage. Short descriptions can match a journey through its cited source titles. If several journeys fit, choose one from the plan. Saving retains the expected outcome, draft steps or missing setup, and a link to the source conversation. It leaves test approval and execution to the review step.
