# Direct API adapters for scenario proposals

Research checked against official provider documentation on 26 September 2026. This is the implementation contract for **API keys** used in managed and bring-your-own-key (BYOK) modes. Consumer subscriptions, CLI sign-in tokens, browser sessions, and OAuth session reuse are outside this operation. Model availability depends on the selected key and must be tested with that key; an allowlisted name alone does not grant access.

## One proposal operation

Keep the existing `internal/planner` proposal workflow: validate consent and inputs, assemble the final context once, hash exactly that context, call one selected provider, decode one JSON proposal, run the existing `qa.ValidateScenario` business checks, and return only unapproved drafts. Preserve the current 90-second deadline, two-call concurrency limit, 6,000 output-token cap, 2 MiB response cap, no redirects, no automatic retry, and no tools. A single `generateJSON(ctx, provider, model, key, instructions, userText, schema)` switch may dispatch to three small concrete request/response functions; it does not need a provider registry or universal chat abstraction. Managed and BYOK choose only the credential source, then run the same provider function. Keep keys out of logs, response errors, model prompts, and browser workers.

Add `provider` (`openai`, `anthropic`, or `google`) to proposal input and result. Replace the single config object with `providers: [{provider, models, managed_available, byok_available}]`; each entry reports only the exact configured model IDs and availability for that provider. Validate the `(provider, model)` pair before dispatch. Use separate comma-separated `QA_OPENAI_MODELS`, `QA_ANTHROPIC_MODELS`, and `QA_GEMINI_MODELS` allowlists and separate server-local managed keys `QA_OPENAI_API_KEY`, `QA_ANTHROPIC_API_KEY`, and `QA_GEMINI_API_KEY`. Do not silently select a model, provider, or payment mode when one fails. Restrict configured model IDs to safe URL/path characters (`[A-Za-z0-9._-]`, at most 100 bytes), especially because the Google model becomes a URL path component. Configure only models whose structured-output capability has been checked with the current official provider documentation and a key-specific probe; do not infer that every model from a list supports the same schema. [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [Claude structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [Gemini structured outputs](https://ai.google.dev/gemini-api/docs/generate-content/structured-output).

The web form must show provider and model together, name the actual recipient in the consent text, and reset consent when provider, model, mode, context, or selected snapshots change. Continue using the transient `X-QA-Provider-Key` only for BYOK. Anthropic documents that multi-workspace keys also require `anthropic-workspace-id`; either support an optional transient workspace ID header plus server-local managed workspace ID, or explicitly accept only single-workspace keys in the first adapter. Never persist a BYOK workspace choice or key in normal proposal records. [Claude API authentication](https://platform.claude.com/docs/en/api/overview).

Use the current instruction as a provider-specific system/instructions field and the existing `Testing request:\n...\n\nApplication context:\n...` as a user field. Preserve the distinction: repository files and browser observations are untrusted evidence, not system instructions. Each provider receives the same selected context and the same proposal JSON schema, with no web search, code execution, or tool definitions. The provider response is a candidate for local validation, never an approval or a business oracle.

## Wire contracts

The snippets show the important fields; `S` is the embedded proposal schema and `U` is the assembled user text. POST JSON only to these fixed HTTPS origins. Refuse redirects, bound reads before JSON decode, and do not copy a provider-supplied URL into a follow-up request.

| Provider | Request | Successful extraction |
| --- | --- | --- |
| OpenAI | `POST https://api.openai.com/v1/responses`; `Authorization: Bearer <key>`, `Content-Type: application/json`; `{"model":"<allowed>","instructions":"<instructions>","input":"<U>","store":false,"max_output_tokens":6000,"text":{"format":{"type":"json_schema","name":"qa_scenario_proposals","strict":true,"schema":S}}}` | Require top-level `status == "completed"`; reject refusal and incomplete responses; accept exactly one `output` message text block with `type == "output_text"`, then parse its `text` as proposal JSON. The existing adapter already follows this shape. [Responses structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) |
| Anthropic | `POST https://api.anthropic.com/v1/messages`; `Authorization: Bearer <key>`, `anthropic-version: 2023-06-01`, `Content-Type: application/json` (plus `anthropic-workspace-id` when required); `{"model":"<allowed>","max_tokens":6000,"system":"<instructions>","messages":[{"role":"user","content":"<U>"}],"output_config":{"format":{"type":"json_schema","schema":S}}}` | Require `type == "message"`, assistant role, a successful natural stop (`stop_reason == "end_turn"`), no refusal indication, and exactly one text content block; parse its `text`. Reject `max_tokens`, refusal, tool use, absent text, or extra content. Current stable JSON-output field is `output_config.format`; old `output_format` needs a beta header and is deprecated. [Messages API](https://platform.claude.com/docs/en/api/messages/create), [structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [authentication headers](https://platform.claude.com/docs/en/api/overview) |
| Google Gemini | `POST https://generativelanguage.googleapis.com/v1beta/models/<allowed>:generateContent`; `x-goog-api-key: <key>`, `Content-Type: application/json`; `{"systemInstruction":{"parts":[{"text":"<instructions>"}]},"contents":[{"role":"user","parts":[{"text":"<U>"}]}],"generationConfig":{"candidateCount":1,"maxOutputTokens":6000,"responseFormat":{"text":{"mimeType":"application/json","schema":S}}}}` | Require exactly one candidate with `finishReason == "STOP"` and exactly one text part in `candidate.content.parts`; parse that `text`. Reject missing candidate, prompt block, `MAX_TOKENS`, safety/other finish reasons, unexpected parts, or absent text. Use the current `responseFormat.text.schema` REST shape rather than mixing it with older `responseJsonSchema` examples. [GenerateContent reference](https://ai.google.dev/api/generate-content), [structured-output REST example](https://ai.google.dev/gemini-api/docs/generate-content/structured-output) |

The Google API reference says prompt blocking can return **no candidates** and reports details in `promptFeedback`; it also defines `STOP`, `MAX_TOKENS`, and safety-related finish reasons. Claude documents 200 responses for refusals and potentially incomplete output at `stop_reason: "max_tokens"`; a provider success HTTP status is not enough. OpenAI likewise documents incomplete and refusal cases. [Gemini response semantics](https://ai.google.dev/api/generate-content), [Claude invalid outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

## Schema and Go type changes before dispatch

`internal/planner/schema.json` currently places `maxItems: 10/20/50` on arrays. Claude's structured-output grammar does **not** support array bounds beyond `minItems` of zero or one, so the current schema would receive HTTP 400. Remove `maxItems` from the wire schema (and preferably remove all array size keywords for one shared provider schema); retain the exact 10-scenario, 20-question, 20-assumption, and 1–50-step checks after decoding. Google documents array bounds, while OpenAI excludes them for fine-tuned models, so local enforcement is the portable rule. Keep `additionalProperties:false` on every object and all object fields required, because OpenAI strict output requires both. Keep step's action-specific fields required but nullable (`["string","null"]`), then use local action validation; this is within Claude's 16-union-field limit and Gemini's documented null type support. [Claude schema limits](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [OpenAI schema subset](https://developers.openai.com/api/docs/guides/structured-outputs), [Gemini JSON Schema subset](https://ai.google.dev/gemini-api/docs/generate-content/structured-output).

The schema has no `approved` property. Continue decoding into `qa.ScenarioInput`, temporarily checking assertion requirements with `Approved=true` as the current planner does, then always return `Approved=false`. Do not let a provider choose approval. Reject unknown fields, missing arrays, extra JSON after the first value, unsupported actions, missing assertions, unsafe paths, invalid test IDs, and overlong strings even if a provider promises schema adherence. A provider's grammar does not verify the operator's expected business outcome.

## Error handling and proof

Keep the public API's existing 400/429/502/503/504 split for invalid request, local saturation, failed provider/output, unconfigured access, and deadline. Internally distinguish at least authentication or model access (401/403/404), malformed schema/request (400/422), rate or quota (429 and provider-specific codes), provider outage (5xx), refusal, and truncated/invalid output, so operators can diagnose configuration without exposing provider bodies, prompts, keys, or sensitive context. Avoid converting a failed required model call into proposals from another provider. Provider error messages can contain input fragments; expose only fixed safe text. OpenAI publishes distinct 429 billing/spend/rate codes; Claude errors have `{type:"error",error:{type,message},request_id}` and 429/529 cases; Gemini standard HTTP errors have an `error` object and publish 429/503 retry guidance. [OpenAI errors](https://developers.openai.com/api/docs/guides/error-codes), [Claude errors](https://platform.claude.com/docs/en/api/errors), [Gemini errors](https://ai.google.dev/gemini-api/docs/api-errors), [Gemini troubleshooting](https://ai.google.dev/gemini-api/docs/troubleshooting).

Fake-transport tests should assert each provider's exact origin, headers, request shape, model allowlist, managed/BYOK credential routing, no redirects or retries, response cap, refusal/incomplete handling, malformed schema/output rejection, and `approved:false`. Add one live paid probe per provider only with an explicitly configured test key and compatible model; the fixture tests cannot establish current account access or model/schema compatibility. Use no production application context in those probes.
